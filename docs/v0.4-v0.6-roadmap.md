# Prajnavex v0.4-v0.6 Roadmap

Status: planned

Theme: model-neutral knowledge core with stable APIs, connectors, and reusable
context contracts.

## Direction

Prajnavex should become an independent structured knowledge core. Codex,
Claude, Obsidian, the Web UI, and future tools are clients of that core.

```text
Prajnavex Core
  -> Knowledge API Kernel
  -> Model Connector Layer
  -> Knowledge Reuse Protocol
```

The Markdown vault and frontmatter schema remain the storage contract. New
capabilities should strengthen retrieval, review, and reuse without making one
model, editor, or UI the system foundation.

## Client Boundaries

- Obsidian is the human workbench: read, edit, link, approve, reject, review,
  and promote knowledge.
- Codex, Claude, and other models are model clients: ingest, transform,
  reason, retrieve, and reuse knowledge through stable interfaces.
- The Web UI is an operational client: expose high-frequency review and
  approval workflows.
- CLI tools remain adapters for batch actions, validation, and local
  automation.

## v0.4: Knowledge API Kernel

Goal: expose Prajnavex knowledge through a stable local interface before
expanding UI or model-specific integrations.

Scope:

- list Sources, Cards, Skills, Bundles, and pending drafts;
- get a note by stable `id`;
- search frontmatter before reading note bodies;
- retrieve candidate notes by type, tag, stage, maturity, and review state;
- create Source/Card drafts through existing ingestion paths;
- approve, reject, or mark drafts as needing rework;
- export bounded context packs for Cards, Sources, Skills, and Bundles.
- define citation and provenance fields for agent-readable context packs.

Structure subdirection:

- Introduce recall stages: `surface`, `trigger`, and `load`.
- Introduce maturity and usage signals without moving existing vault folders.
- Treat the referenced knowledge-system architecture as conceptual input, not
  as a folder blueprint.

Acceptance:

- Web UI and CLI can call the same local API for core read/review operations.
- A model client can request a bounded context pack without reading raw vault
  folders directly.
- Existing validation, audit, and v0.3 ingestion tests still pass.
- A local read-only context-pack adapter returns bounded bodies, stable IDs,
  provenance, confidence, staleness, and citation metadata.

## v0.5: Model Connector Layer

Goal: let multiple model environments use Prajnavex through adapters instead
of direct vault assumptions.

Candidate connectors:

- Codex adapter;
- Claude or MCP adapter;
- generic local HTTP client;
- CLI adapter for scripted workflows.

Connector rules:

- Model clients request knowledge through API operations and context packs.
- No connector may promote drafts into stable knowledge without explicit human
  approval.
- Privacy and local-first behavior remain defaults.
- Model-specific prompt formats live at the adapter edge, not in the core
  schema.

Acceptance:

- At least two client surfaces can retrieve the same Card or Skill context
  through the same kernel contract.
- Connector logs identify requested IDs, returned pack types, and approval
  boundaries without logging secrets.

## v0.6: Knowledge Reuse Protocol

Goal: standardize how reusable knowledge leaves Prajnavex.

Context pack types:

- `source_evidence_pack`: source identity, provenance, evidence, and review
  state.
- `card_context_pack`: one reusable idea with source link, confidence,
  caveats, and related Cards.
- `skill_execution_pack`: trigger, inputs, procedure, outputs, pitfalls, and
  source Cards.
- `bundle_workflow_pack`: multi-skill workflow with input/output contracts and
  execution order.

Acceptance:

- Packs are bounded, cite stable IDs, and include enough metadata for audit.
- Packs can be consumed by Codex, Claude, and the Web UI without format
  rewriting.
- Usage and review signals can feed future retirement, promotion, or archive
  decisions.

## Non-Goals

- No cloud-only dependency.
- No autonomous promotion, merge, or deletion.
- No Obsidian plugin dependency as a prerequisite.
- No vector database requirement before frontmatter-first retrieval is stable.
- No physical vault migration until the API and contract layer prove the need.
